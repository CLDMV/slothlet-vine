# Slothlet Vine v1.3.0 Changelog

**Release Date**: October 2026
**Release Type**: Minor
**Branch**: `next` → `master`

---

## Overview

A call can now carry a context of its own. Until now, everything a served leaf knew about its caller came from the channel: `serve({ principal })` binds one identity to the connection, and the `call` frame deliberately carries none. Applications also need context that the caller chooses per call and that is not identity, such as the project a user has open, where one browser window works in project A and another in project B, over the same socket or separate ones. Keeping that in the principal makes the server hold per-connection state that races with in-flight calls whenever it changes, and passing it as an argument means threading a parameter through every leaf.

v1.3.0 adds a **requested context**: an optional, data-only object on the `call` frame. The grow side sets it per call with `link.with(context, fn)` or as a link-wide default with `grow({ context })`. The serve side decides what to believe through a new `serve({ context })` host check, which can accept the request, narrow or change it, or refuse it. Whatever the check accepts is merged into the call's context scope under the principal's keys, every key write-protected, so the permission gate, rule conditions, `around` and the leaf all see it and none of them can rewrite it. The server holds no state about it.

The feature is opt-in on both ends. A serve without a `context` check and a grow that never sets a context send and answer exactly the frames they did in v1.2.x. The frame version is unchanged, and the `@cldmv/slothlet` peer range is the same (`>=3.22.0`, optional `ws >=8.0.0`).

## ✨ Features

### `serve({ context })`: the host check for a requested context ([#80](https://github.com/CLDMV/slothlet-vine/pull/80), [#79](https://github.com/CLDMV/slothlet-vine/issues/79))

`context: (requested, { principal, path, args }) => object | false | null | undefined`, and it may be async. It runs only for a `call` frame that carries a requested context, after the principal is resolved and before the permission gate. It receives a private copy of the request, the resolved principal (`null` on a serve without one), the leaf path, and the frame's arguments as a rule condition would see them.

- **Accept** by answering a plain object: the request itself, or a narrowed or changed one. The answer is copied, so the host's own object is never shared with the scope. Dropping a key narrows the request, and changing a value canonicalizes it.
- **Refuse** by answering anything else (`false`, `null`, a non-plain object, an object holding a function) or by throwing or rejecting. A refusal is the new `VINE_CONTEXT` error and the leaf never runs. The host's own error never crosses the wire, and the message names the path only.
- **Without a check, a requested context is refused**, never silently ignored, so a client can never believe a call is scoped when it is not.
- **Setup fails closed.** A `context` that is not a function throws a `TypeError`. So does an instance whose `api.slothlet.context.scope` does not work (for example a `scope: false` instance), and nothing is published in that case. A principal is not required: a check alone needs a working scope, not the permission system.

```javascript
await serve(api, createChannel(socket), {
	paths: ["project"],
	principal: { path: "remote.renderer", context: { actor: { id: user.id, roles: user.roles } } },
	context: async (requested, { principal }) =>
		(await projects.canAccess(principal.context.actor.id, requested.project)) ? { project: requested.project } : false
});
```

The pipeline for a frame carrying a requested context, with a principal: `VINE_NO_LEAF` → resolve the principal → `VINE_DATA_ONLY` if the request is not data → the `context` check (`VINE_CONTEXT` unless it answers a plain, data-only object) → open the scope with the accepted keys merged under the principal's, every key write-protected → the gate (`checkCall`) → the argument scan → invoke → result. Without a principal the same, minus the gate. A frame with no requested context never reaches any of this.

| Requested context on the frame | `context` check answers        | Scope the gate and leaf see      | Outcome                                             |
| ------------------------------ | ------------------------------ | -------------------------------- | --------------------------------------------------- |
| none                           | not called                     | the principal's context only     | as in v1.2.x                                        |
| `{ project: "p1" }`            | the request                    | `{ project: "p1", actor }`       | the rules decide, with `ctx.project === "p1"`       |
| `{ project: "p1", debug: 1 }`  | `{ project: "p1" }` (narrowed) | `{ project: "p1", actor }`       | `debug` never reaches anything                      |
| `{ project: "p2" }`            | `false` (no access)            | no scope is opened               | `VINE_CONTEXT`; the rules are never asked           |
| `{ actor: { id: "root" } }`    | the request                    | `{ actor }`, the principal's own | the principal key wins; the request cannot override |
| `{ project: "p1" }`            | no check configured            | no scope is opened               | `VINE_CONTEXT`                                      |
| `{ cb() {} }` or `"p1"`        | not called                     | no scope is opened               | `VINE_DATA_ONLY`                                    |

A refused request (`VINE_CONTEXT`) is deliberately distinct from a rules refusal (`VINE_DENIED`): a client can tell "this context is not yours" and unpin the project, apart from "you may not call this". An accepted context that the rules then refuse is still `VINE_DENIED`.

`serve({ around })` receives the accepted context as a new `context` property on its call argument: a private copy, or `null` when the frame carried none. It runs inside the scope that holds it.

### `link.with(context, fn, ...args)` and `grow({ context })`: sending a requested context ([#80](https://github.com/CLDMV/slothlet-vine/pull/80), [#79](https://github.com/CLDMV/slothlet-vine/issues/79))

`link.with(context, fn, ...args)` runs `fn` with a requested context on every call it makes over that link, directly or through any module and across every `await`, and resolves to `fn`'s value.

```javascript
await link.with({ project: "p1" }, () => viewApi.project.files.list());
```

- **The context lives on the call, not the channel.** Two extents over one link carry different contexts at the same time, a later `with()` never races a call already in flight, and calls over a different link are untouched.
- **The innermost extent wins, with no merge.** `with(null, fn)` clears the context for a nested extent, and the link default does not apply there either.
- **It is copied once.** The context is checked by the same data-only rules as arguments, with a plain-object shape on top, and then copied, so mutating the original afterwards changes nothing. A non-plain or function-bearing context rejects with `VINE_DATA_ONLY` naming where the fault is (for example `context.onDone`) before anything runs. `with()` runs `fn` inside `api.slothlet.context.scope()` on the grow instance, so that instance must not be `scope: false`.
- **Only the link's own extents count.** The extent travels as a holder function minted by that link under a key private to it, and a function a grow-side module plants under the same key is ignored.

`grow(api, channel, { context })` sets the link's default: a plain object (validated and copied once), or a function called synchronously on every call that answers an object, or `null` / `undefined` for none. A resolver is how a client sends whatever it currently has pinned without the far side holding any state. A resolver that throws rejects that call with its own error, and a non-data answer rejects it with `VINE_DATA_ONLY`. A bad static default fails `grow()` itself, and a `context` that is neither a function nor an object throws a `TypeError`.

The resolved `link` also gains `link.context`, a boolean: whether the far side accepts a requested context.

A call that would carry a requested context is **refused locally** with `VINE_CONTEXT`, and nothing is sent, when the far side did not advertise that it accepts one. An older serve would drop the unknown key and run the call unscoped, and the caller would never know.

### `VINE_CONTEXT` error code ([#80](https://github.com/CLDMV/slothlet-vine/pull/80), [#79](https://github.com/CLDMV/slothlet-vine/issues/79))

`CODES.CONTEXT` (`"VINE_CONTEXT"`) is exported alongside the existing codes. A serve answers it for a refused requested context, and a grow produces it locally for a context sent to a far side that does not accept one. Like every `VINE_*` code that originates on the far side, it reaches the grow side as a `VineRemoteError` with `.code === "VINE_REMOTE"` and `.remoteCode === "VINE_CONTEXT"`.

### Wire format ([#80](https://github.com/CLDMV/slothlet-vine/pull/80))

Two optional keys, no frame version change:

- A `surface` frame carries `context: true` only when the serve has a `context` check. Without one it is byte for byte the v1 frame. Only a literal `true` counts.
- A `call` frame carries `context` (an object) only when the caller sent one. `parseFrame` carries it through raw, and the serve validates it, so a bad one is answered with `VINE_DATA_ONLY` instead of being dropped and left to run into the caller's budget.

`schemas/frame.schema.json` lists both keys as optional, so the v1 shapes remain valid.

## 📚 Documentation

- **NEW:** [docs/changelog/v1/v1.3.0.md](./v1.3.0.md): this changelog.
- `docs/PERMISSIONS.md` gains a "Per-call requested context" section: the pipeline order, the outcome table above, and three recorded decisions. A serve without a check refuses rather than ignores. A requested context is a request, not identity, so the check is where the host ties it to the principal, and rules that matter should still be written against the principal. Events carry no requested context in v1: a `sub` frame has no `context` key, because a subscription outlives any one call.
- `docs/CONFIGURATION.md` documents `serve({ context })`, `grow({ context })`, `link.with()` and `link.context`, and the extended `around` argument. `docs/DESIGN.md` lists the two optional frame keys. `docs/ERRORS.md` adds `VINE_CONTEXT` and extends `VINE_DATA_ONLY` to cover a requested context that is not data.
- `docs/TRANSPORTS.md` points to a requested context for per-call state a page chooses, and `docs/CUSTOM-TRANSPORTS.md` now tells transport authors to carry every key of a frame, including ones they do not recognize: frames grow optional keys without a version bump, and a transport that copies only the keys it knows would silently strip `context`.

## Upgrade notes

- **No breaking changes to the public API.** Every addition is optional: `serve({ context })`, `grow({ context })`, `link.with()`, `link.context`, `CODES.CONTEXT` and `around`'s new `context` property. A serve without `context` and a grow that sets none behave as in v1.2.x, and the wire format only gains optional keys.
- **One behavior to know about.** Before this release a serve ignored an unrecognized `context` key on a `call` frame. A serve now refuses such a frame with `VINE_CONTEXT` unless it has a `context` check. The grow shipped in earlier releases never sends one, so this only affects frames built by hand.
- **Mixed versions.** An older grow talking to a v1.3.0 serve works unchanged, and the check is not asked. A v1.3.0 grow facing an older serve sees no `context` on the surface (`link.context === false`) and refuses a requested context locally, while plain calls work. The host must not rely on a requested context where the serve is older than v1.3.0.
- **Custom transports** must pass every frame key through untouched. If a transport rebuilds frames from a fixed key list, it will drop `context` and the serve will then treat the call as having none.
- **Adopting it.** Add a `context` check to `serve()`, ideally one that ties the request to the verified principal, and send the context from the page with `link.with()` or `grow({ context })`. The serving instance needs a working `context.scope`, and the grow instance does too for `with()`.
- The setup error for a principal on an instance whose `context.scope` or `context.run` does not work now reads "needs a working `api.slothlet.context.<name>()` to run each call under its context", since the same probe also guards the new check. It is the same `TypeError` raised at the same point.
