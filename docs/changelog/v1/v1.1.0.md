# Slothlet Vine v1.1.0 Changelog

**Release Date**: September 2026
**Release Type**: Minor
**Branch**: `next` → `master`

---

## Overview

v1.1.0 carries slothlet's instance-wide **events** across a vine, **in both directions** (#20). An event emitted in either linked instance reaches subscribers in the other, as if the two were one api — which they effectively are: the instances are copies of the same tree (per-leaf stubs at identical paths) and therefore hold the same event permissions.

This is purely additive. Call forwarding, the frame protocol, the error taxonomy, and every transport are unchanged; a consumer that does not subscribe to or emit forwarded events sees nothing new. Event forwarding needs the two `api.slothlet.*` primitives that shipped in `@cldmv/slothlet` 3.18.0 — and, for a **same-process** transport (the loopback, or any grow/serve pair sharing a process), the cross-instance caller-isolation fix in **3.18.1** (see **Dependencies** and **Upgrade notes**).

---

## ✨ Features

### Cross-vine event forwarding (#20)

Both ends expose an event surface identical in shape to slothlet's own — `link.event.on` / `link.event.once` on the grow side, and the serve handle's `event.on` / `event.once` on the serve side — async, because the granted delivery level is resolved across the boundary:

```js
const { level, off } = await link.event.on("orders.created", (payload, meta) => {
	// meta is { event, at, instanceID }; payload is undefined at `notify`.
});
```

slothlet gates **subscribers**, never emitters, resolving each to one of three levels — `deny` (nothing), `notify` (a trigger, no payload), `allow` (trigger + payload). The vine adds exactly one boundary rule: **a subscriber only ever receives what its level allows, and nothing more is ever put on a wire heading toward it.** The **emitting** side resolves each far subscriber against its own rules and forwards only what that level permits — so a `notify` subscriber's payload never leaves the emitting instance — re-resolving on every emit so a live rule change is honoured. The granted level is returned to the subscriber as a distinct, catchable `{ level }`, never a silent absence of payloads, so a policy or version mismatch is observable rather than a mystery. Payloads remain data-only: a function anywhere in a payload degrades an `allow` delivery to trigger-only rather than crossing.

### Bidirectional — either instance emits, either subscribes

Because the two linked instances are copies with identical permissions, forwarding is symmetric with no trust flag, no authority handoff, and no gate on who may emit — the emitting side resolves and cuts, whichever side that is. Each end runs both halves at once over one channel; the two never cross wires (each draws its subscriptions' correlation ids from its own space, and frames route by type). The confidentiality direction (a trusted emitter → a far subscriber) and the reverse (a far emitter → a local subscriber, gated locally by the same rules) are the same mechanism.

The wire adds four frames — `sub`, `sub-ack`, `event`, `unsub` — correlated on their own `subId` space, separate from the call `callId` space. See [docs/DESIGN.md](../../DESIGN.md) § Event forwarding.

Full suite green. ## Upgrade notes

A drop-in for v1.0.x for existing call-forwarding code — nothing to do. Event forwarding is additive; adopt it only if you subscribe to or emit forwarded events.

**If you use forwarded events, note the slothlet floor.** The two enablers are present from `@cldmv/slothlet` 3.18.0, but a **same-process** transport (the loopback, or any grow/serve pair inside one process) requires **≥ 3.18.1** — 3.18.0 has a cross-instance caller bug that silently drops same-process deliveries. A real cross-process boundary (worker, process, socket) is unaffected and works on 3.18.0+. An instance whose slothlet predates the enablers degrades gracefully: a `sub` it cannot gate is refused with a catchable `deny`, and `event.on` throws a clear `TypeError` rather than forwarding ungated.
